# Restore keeps the Import identity and re-derives its digest for the restored Accounts

ADR-0007 freezes the Import duplicate identity (User, Account, date, signed file amount, Raw Statement Description) as a digest stored at commit. `user:restore` breaks that rule in two ways. It deletes the User's data and recreates the Accounts, so every Account gets a new id, yet the Account id of the identity (`import_identity_account_id` on a Financial Operation and a Capital Movement, `source_` and `destination_import_identity_account_id` on an Own Transfer) goes to the database as written in the snapshot. On an empty database the ids happen to coincide and the restore passes; on a User who already has data it fails on the foreign key (SQLSTATE 23503). And the stored digest hashes the old Account id (and the source User id), so even where the restore passes after a rename of ids, no newly computed digest ever equals it and the Import duplicate detection goes silently off. The trial of S-21 on a copy of production found both (`context/archive/2026-11-11-category-merge/merge-trial.md`, O1): the snapshot carries the identity in 1269 of 1280 operations. The way back for the category merge (ADR-0078) and for the snapshots of `deploy.sh` is `user:restore` onto a User with data, so this must work before the deployment. This ADR adds to ADR-0007; the definition of an Import duplicate does not change.

Decision. The identity is made of the User, the Account, the date, the amount and the Raw Statement Description, not of row ids. A restore gives new ids, so it carries the identity over by its fields: the Account of the identity goes through the same Account map as every other Account id of the snapshot, the date and the amount are copied as written, and the digest is computed again by `ImportIdentityDigest` from the restored User, the new Account id, the stored date (the `Y-m-d` string, not a Carbon object, because the string enters the hash), the stored amount and the stored Raw Statement Description of that record. The old digest is never copied and never compared. Raw Statement Description does not change after the commit (every edit rule prohibits it), so the recomputation rebuilds the input of the commit.

Which legs. A Financial Operation, each leg of an Own Transfer (the source leg hashes `source_raw_statement_description`, the destination leg `destination_raw_statement_description`) and a Capital Movement. A Capital Movement and the Income Operation of the same file row keep the same identity, because both store the same Raw Statement Description. A leg without a digest in the snapshot did not come from an Import: the restore maps its Account id (when it has one) and computes no digest, so a hand-entered record never becomes an Import duplicate.

Refusal. A record with a digest in the snapshot needs all the inputs: an identity Account that is in the snapshot, a date, an amount and a Raw Statement Description (an empty string is a value, `null` is not, as in `ImportIdentityDigest::compute()`). When one is missing, or the identity Account is not among the restored Accounts, the restore throws `UserSnapshotException` naming the record and the field, the transaction rolls back and the data of the User stays as it was. The same holds for an identity Account outside the snapshot on a leg without a digest, because the raw id would break the foreign key.

Example. A snapshot of User 1 has Account 3 „mBank” and an Expense with identity Account 3, date 2026-05-14, amount −4 599 and the description of the file row. It is restored onto User 8 (or onto User 1 again); „mBank” is recreated as Account 12. The Expense gets identity Account 12 and the digest `sha256(8 | 12 | 2026-05-14 | −4599 | description)`. A later preview of the same statement row on Account 12 computes the same digest and shows the row as an Import duplicate.

We rejected:

- copying the digest unchanged (it hashes the old ids, so no new row would match it and the detection would be off for 1269 of 1280 operations without a sign of it);
- clearing the identity on restore (the same loss, and the next import of the statement would double the operations);
- keeping the old digest and warning (the warning would not bring the detection back, and the User cannot act on it);
- checking the stored digest against the old User and Account ids before recomputing (a second rule that can only refuse files the recomputation reads correctly; the manual trial checks the counts instead);
- a new snapshot version (the fields are already in version 10; the recomputation works for every version that carries the identity).

Consequences. `RestoreUserData` computes the identity in one class under `app/Support/UserSnapshot/`, which the three places that write it call. The Capital Movement, which already mapped its identity Account and refused an unknown one, now also gets a recomputed digest. A snapshot with a digest but without its inputs, which loaded before on an empty database, is now refused. The format of `BackupUserData` stays untouched, and a snapshot written earlier (also by the merge action and `deploy.sh`) loads with the digest computed for the restored User.
