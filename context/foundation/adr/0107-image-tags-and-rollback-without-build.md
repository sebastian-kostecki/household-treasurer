# Image tags beside `:prod` and a rollback without a build, locked by the migrations

Every `scripts/deploy.sh` rebuilt `household-treasurer-app:prod` in place, so the previous image became dangling and the only way back was `git revert`, a push, a `git pull` on the server and a full build on the shared CPU, with the application in maintenance mode for minutes. Nothing removed the dangling images either. This ADR implements step 2 of `context/foundation/infrastructure.md` differently from how it is written there and complements ADR-0064 (the instance backup stays in `deploy.sh`).

`:prod` stays a pointer. `docker-compose.prod.yml` keeps `image: household-treasurer-app:prod`; `deploy.sh` tags the built image with the short SHA of `HEAD` next to it, so the SHA tags are history and `:prod` is what runs. This departs from `household-treasurer-app:${APP_IMAGE_TAG:-prod}` in infrastructure.md: any Compose call made without the variable (`scripts/artisan.sh`, a manual `docker compose exec`) would silently resolve to a stale `:prod` and raise it.

Labels carry the facts. The last instructions of the `runtime` stage of `Dockerfile.prod` set `org.opencontainers.image.revision` (the commit) and `household-treasurer.deployed-at` (UTC, set by `deploy.sh` once per deployment). They come last, so a value that changes on every build invalidates no layer. The order of deployments comes from `deployed-at`, not from the image's `.Created`: BuildKit keeps the date of the cached layer, a deployment of a commit that only touches `context/`, `scripts/` or `tests/` (all in `.dockerignore`) is fully cached and ties with the previous one, and the rebuild after a `git revert` gets the old date. An image from before the tags (`:prod` without the `revision` label) is tagged `legacy-<YYYYMMDD of its creation>` before the build, because afterwards it loses `:prod`; its sort key falls back to `.Created`.

Cleanup. After a successful deployment `deploy.sh` keeps the 3 newest tags by `deployed-at`, never removes a tag whose image is the current `:prod` or the image that was `:prod` before this deployment (it may be older than the three newest after a rollback and then redeployment of a bad commit), and runs `docker image prune -f --filter label=maintainer=household-treasurer`. The label is already in `Dockerfile.prod` and in the old images, and it limits the prune to this application: halina175 is shared with other stacks. The build cache stays, because it makes the rebuild after a `git revert` quick.

Rollback. `scripts/rollback.sh` lists the tags, and `scripts/rollback.sh <tag>` switches `:prod` to that image and runs `up -d --no-build app` through maintenance mode, then permissions and caches, like `deploy.sh`. The migration lock runs first and in both directions, with no confirmation prompt: migrations in the `migrations` table that the target image does not have stop the script with the list and the command `scripts/artisan.sh migrate:rollback --force` (the code that has their `down()` still runs); migrations of the target image that the database has not run stop it too and point to `scripts/deploy.sh`, because new code cannot serve a request on the old schema. `rollback.sh` never migrates and makes no user snapshot, instance backup or control numbers: switching the image does not change data, and the lock guarantees a schema that fits the code. It does not touch git, so the server stays on the bad commit and the way ends with `git revert`, `git pull --ff-only` and `deploy.sh`.

We rejected:

- `${APP_IMAGE_TAG}` in Compose (any call without the variable raises a stale `:prod`, see above);
- a warning with a confirmation instead of the lock (the operator under stress confirms; the lock costs one extra command and leaves the application untouched);
- a description in the README only, without a script (the order of maintenance mode, switch, `up -d` and caches is exactly what gets forgotten);
- `docker builder prune` in this change (it would slow the rebuild after a `git revert`; disk monitoring is a separate risk in infrastructure.md);
- ordering by `.Created` (BuildKit keeps the date of the cached layer, see above);
- a bare `docker image prune -f` and `--filter "until=168h"` from infrastructure.md (the server is shared with other applications, and age says nothing about which image we may need to return to; the `label=maintainer=household-treasurer` filter replaces it);
- letting pending migrations through on rollback (it would make `rollback.sh` a second, weaker `deploy.sh` without the backups and control numbers).
