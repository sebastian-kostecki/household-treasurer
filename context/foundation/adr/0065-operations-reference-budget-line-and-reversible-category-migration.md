# Operations point at a Budget Line, and the Category list migration is reversible

ADR-0063 moves the Category to the User and makes the yearly record a Budget Line, and ADR-0064 puts a copy of the instance before every production migration. Neither says what the Financial Operation and the Month Plan item point at in the database, how the name key is stored, what a request means by `category_id`, or how S-18 is undone after a deployment. This ADR settles those and corrects one example; it changes none of the rules (a)–(f) of ADR-0063, which stays as it is.

Reference. A Financial Operation and a Month Plan item point at a Budget Line (`budget_line_id`), and through it at the list Category in the Budget of the operation’s year or of the plan’s month. The table `categories` of today is renamed `budget_lines` and keeps its ids, and the new `categories` table holds the list. So `financial_operations.budget_line_id` and `month_plan_items.budget_line_id` hold exactly the values that `category_id` holds today, and the migration rewrites no value in the 1 271 operations and the 38 plan items; only the name of the column changes. Execution stays on the same row it was written to. `unique(budget_id, category_id)` on `budget_lines` and `unique(user_id, type, name_key)` on `categories` are the last line of defence for the rules.

Name key. `name_key` is a stored column, computed by one PHP function (`CategoryNameKey::of`: Unicode trim, then `mb_strtolower`). It is not a database expression because PostgreSQL `lower()` depends on the collation of the database, and the migration, the conversion of snapshots and the validation must compute the same key. The steps (a)–(d) of ADR-0063 are one class on plain arrays (`LegacyCategoryConversion`), used by the data migration and by the restore of snapshots 1 to 5, so both give the same list from the same data. The class is frozen: a change to it changes the meaning of a migration that has already run.

The `category_id` on the HTTP boundary. Until the views move to the list (S-18, phases 3 and 4) a request and a prop still carry the id of a Budget Line under the old key `category_id`. From phase 4 `category_id` on the boundary is always the id of the list Category, and the server finds the Budget Line itself, in the Budget of the year of the date or of the page. A request never carries a Budget Line id after that.

Reversible migration. Expand, backfill and drop are three migrations of one deployment, and `down()` of each really reverses it: it renames tables, columns and constraints back, drops what the migration added and writes the names from the list into the old columns, so a Category created or renamed after the deployment comes back as an ordinary record of its Budget with the spelling of the list. A test on PostgreSQL covers the migration and `down()`. The backfill checks itself in its own transaction (every Budget Line has a Category of the same type; the number of Budget Lines, the sum of Execution, Initial Plan and Current Plan per Budget are unchanged; every Financial Operation and every Month Plan item points at a Budget Line of its own Budget) and an exception rolls the backfill back. Control numbers compared before and after the migration stop the deployment (S-18, phase 6). The way back after a deployment keeps the operations added since: `migrate:rollback` with the new code, then the old code.

Correction of ADR-0063. The dev example „2026 #46 becomes „Rozrywka (2)” and is active, the same for „Odsetki” and „Odsetki (2)”” is wrong: #46 and the records called „Rozrywka (2)” and „Odsetki (2)” belong to the second User (Budget #2), not to the first User’s Budget, and no User has the same name key twice in one Budget on dev or in production. The rule (b) does not change; its test builds the „(2)” case by hand.

We rejected:

- pointing the Financial Operation straight at the list Category (it rewrites 1 271 operations and 38 plan items, and loses which year’s line an amount belongs to);
- a `down()` that restores the exact old names (it needs dead columns kept for the sake of a rollback; the names come from the list);
- only the copy of the instance as the way back (it loses every operation added after the deployment);
- the name key as a database expression or a generated column (collation-dependent, and a second implementation of the rule).
