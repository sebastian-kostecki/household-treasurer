# Snapshot

## Every snapshot version ever written must still restore

`BackupUserData::SNAPSHOT_VERSION` is the version `user:backup` writes. `RestoreUserData` lists the accepted versions explicitly and uses the constant for the newest one. When you bump the constant: add the previous number to every version list in `RestoreUserData`, give new fields defaults for older snapshots (for added fields; a changed shape is converted, see below), and add a restore test for each older version in `tests/Feature/UserSnapshotCommandTest.php`, so existing backups keep loading (FR-014).

## An older snapshot is converted, not just defaulted

When the model changes shape, restoring an older snapshot goes through the same rules as the data migration, so a restored snapshot equals what the migration would make of the same data. Version 6 (S-18) writes `categories` (the User's list) and `budget_lines` (the yearly records, `category_id` pointing at the list, operations and Month Plan items with `budget_line_id`); a v6 line has no type of its own (the type is the list Category's), and the restore refuses a line that points at an unknown Category, two lines of one Category in one Budget, and a Financial Operation or Month Plan item whose line belongs to another Budget. Version 7 (S-19) adds `description` to every Category of `categories`; version 6 restores with `description = null`, and so does the conversion of versions 1 to 5. Version 8 (S-22) adds `category_groups` (id, name, type, sort order) and `category_group_id` on every Category; it is required only in 8, and 6 and 7 restore without groups. The restore refuses a Category pointing at an unknown group or at a group of another type, and two groups with the same name key in one type. Version 9 (S-24) adds `rhythms` (Rhythm, start year, start month) to every Category of `categories` and no longer writes `is_paced` and `month_item_kind` on `budget_lines`; the restore refuses an expense Category without an entry, an income Category with one, an unknown Rhythm, a month outside 1 to 12 and two entries starting in one month. Versions 1 to 8 carry the flags instead: the restore keeps them only as the input of `App\Support\CategoryList\LegacyRhythmConversion`, the frozen class the Rhythm backfill uses, and a Category without a line is Running from the month of the restore (ADR-0070). `RestoreUserData` treats 6, 7, 8 and 9 as the list format (`LIST_FORMAT_VERSIONS`), so a new version after 9 adds its number to that list as well. A snapshot of version 1 to 5 holds one flat `categories` list per Budget and goes through steps (a)–(f) of ADR-0063 with `App\Support\CategoryList\LegacyCategoryConversion`, the frozen class the migration uses (`.ai/rules/migrations.md`).

The test in `tests/Feature/UserSnapshotCommandTest.php` restores `tests/Fixtures/snapshots/v5-category-list.json`, a hand-written v5 file (not built from factories, so it does not change with the code) with four cases: the same name in two Budgets, the same name key twice in one Budget („Rozrywka (2)”), a Category present only in an old year (archived), and names differing in letter case or spaces. A parity test checks that the same old shape gives the same list and line assignments through the migration and through the restore of that fixture. `tests/Fixtures/snapshots/v6-category-list.json` is the hand-written v6 file restored by its own test, and `tests/Fixtures/snapshots/v8-category-list.json` the hand-written v8 file with flags (One-off + Running, Bill) whose restore gives the Rhythm the migration would make of the same lines. A snapshot of version 6 made after S-18 does not load in the code before S-18; the way back after a deployment is `down()` (README → „Wycofanie S-18”).
